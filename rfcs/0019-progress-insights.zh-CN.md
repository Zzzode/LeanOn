# RFC 0019 — 进度洞察与周回顾

- 状态：Accepted
- 创建时间：2026-10-02
- 相关文档：RFC 0004（领域引擎）、RFC 0017（运动记录）、RFC 0010（体重写入路径）

## 摘要

当前 LeanOn 只有一个以“当天”为中心的 Home 页面：展示当前热量预算、今日体重摘要、今日宏量营养与今日运动。然而，减肥成败是以“周”而非“小时”为单位的。每日称重与摄入都有噪声，缺少更长周期的视图，用户就无法判断自己是否在正轨上、平台期无从察觉，也丢失了看到积累性进步所带来的动力。本 RFC 新增第二个界面——**Insights（洞察）**，通过顶部的 Today / Insights 分段切换进入，支持 7 天与 30 天窗口。它完全基于 `HostData` 中已有的记录构建，不需要新的原生 RPC、存储字段或网络能力。

## 动机

产品的核心承诺是让用户成功减重并长期保持。行为学研究与主流应用（Noom、WW、MyFitnessPal、Apple 健康）在每日记录之外，都收敛到三点：

1. **看趋势而非噪声。** 单次称重会随水分、糖原和睡眠波动。一周或一个月的拟合斜率，才是能量平衡是否正确的诚实信号。
2. **依从性反馈。** 了解有多少天吃在预算内、平均摄入是多少，能把模糊的“我做得好不好”变成具体数字和可实现的目标。
3. **进步强化。** 展示累计减重、活跃天数和记录天数，能奖励正确行为，并在平台期防止动力流失。

底层数据（35 天体重、两周摄入、运动条目）在宿主端都已存在，缺的只是聚合与展示的位置。

## 目标

- 在 `@zzzode/core` 中新增纯且确定性的聚合器，把已有记录与日期窗口转换为单个 `ProgressInsights` 结果。
- 新增 Insights 界面，含 7 天 / 30 天切换与 Today / Insights 分段开关，且不影响现有 Home。
- 展示：窗口内体重变化、拟合的每周体重斜率（kg/week）、小型趋势图、平均每日摄入、达标天数、平均缺口、活跃天数、运动总量与记录坚持情况。
- 离线可用，并与应用其余部分保持双语（英文 + 简体中文）。

## 非目标

- 不新增 RPC、不做同步、不做服务端；界面聚合宿主已提供的 `HostData`。
- 本切片不做目标、连胜、徽章或社交对比。
- 不做食物级或分餐分析，仅统计每日能量总量。
- 不做报告导出或分享。
- 暂不做月经周期或体脂趋势分析。

## 方案

### 日期窗口

所有计算沿用引擎其余部分（`util/date.ts`）的做法，在 UTC 下按整天进行。窗口由含端点的 `endDate`（通常为今天）与正整数 `windowDays` 描述；含端点的起始日为 `endDate - (windowDays - 1)` 个整天。新增逆函数 `isoFromDayIndex(index)`，把整天索引转回 `YYYY-MM-DN`。当记录日期满足 `start <= date <= end` 时纳入。

### 聚合（`core/insights.ts`）

`buildProgressInsights(input): ProgressInsights` 接收：

```
{
  endDate: string;
  windowDays: number;            // 7 或 30
  weights:   readonly WeightSample[];
  intake:    readonly IntakeSample[];
  exercises: readonly ExerciseSample[];
  dailyBudgetKcal: number;       // 自适应 TDEE 能量目标
}
```

返回：

- **体重**
  - `startWeightKg` / `endWeightKg`：窗口内首次与末次体重，`changeKg = end - start`（负值为下降）。
  - `slopeKgPerWeek`：对窗口内体重做普通最小二乘拟合（复用 `linearTrend`），以每周为单位，并给出 `r2`；当不同日期的体重少于两个时为 `null`。
  - `points`：窗口内用于绘图的 `{ x, y }` 体重点。
  - `weightLoggedDays`：有体重记录的不同日期数。
- **营养**
  - 摄入按日历天求和（多餐累加，与现有 `writeIntake` 行为一致），形成 `dailyKcal: { date, kcal }[]`。
  - `loggedDays`：有任何摄入记录的不同日期数。
  - `onTargetDays`：当日总量 `<= dailyBudgetKcal` 的天数。
  - `averageKcal`：仅对**有记录的天数**取均值；无则为 `null`。
  - `averageDeficitKcal = dailyBudgetKcal - averageKcal`；无记录天数时为 `null`。仅对有记录天取均值，可避免把“没记录”当成“吃了零卡”而虚高平均值。
- **运动**
  - `activeDays`：至少有一条运动记录的不同日期数。
  - `totalKcal` 与 `totalMin`：窗口内所有条目求和。

`windowDays` 必须为有限正整数，否则抛出 `RangeError`。聚合器为纯函数并具备完整单测，包括空窗口与部分窗口。

### 界面（pages）

- 屏幕顶部新增 **Today / Insights** 分段控件；Today 原样渲染现有 Home，Insights 渲染新界面。
- Insights 界面含 **7d / 30d** 分段切换与若干卡片：
  - **体重卡片**：窗口内净变化（带符号，下降用主绿、上升用超预算红）、拟合的 kg/week 斜率，以及由原生视图绘制的紧凑趋势图——一排竖向柱条，柱高编码体重，无需引入图表依赖。
  - **营养卡片**：平均每日摄入、达标天数（以“达标 / 已记录”表示）、平均每日缺口。
  - **运动卡片**：活跃天数与运动总千卡 / 总分钟。
  - **坚持情况行**：窗口内记录体重的天数与记录摄入的天数。
- 聚合在现有 selector/state 层中，使用 Home 已展示的当前自适应预算完成，无需改动 bridge。
- 所有标签加入 i18n 目录（英文为权威，简体中文以 `satisfies Record<MessageKey, string>` 提供）。

### 边界情况

- 窗口内体重少于两个：隐藏斜率与图表，显示中性的“数据尚不足”标签；若存在一个体重，仍展示端点变化。
- 无摄入记录天数：均值与缺口显示中性标签而非 `0`，从而绝不把缺数据误当作断食。
- 窗口延伸到最早记录之前时，仅聚合实际存在的日期，不补造零卡天。
- 同一天多餐、多条运动按上述方式累加 / 每天只计一次。

## 考虑过的替代方案

- **只保留每日 Home。** 已否决：无法区分趋势与每日噪声，也缺少长期强化，而这正是产品目标的核心。
- **引入第三方图表库。** 本切片否决：用视图搭出的柱行已能表达趋势，保持包体小且在 Lynx 运行时中渲染一致；更丰富的图表可日后再议。
- **在原生宿主计算洞察。** 已否决：聚合是针对 JS 层已有数据的纯展示逻辑；放在 core 中可单测、可与未来服务端共享，也避免同时改动两套原生实现。
- **对所有日历天平均摄入（把空缺当零）。** 已否决：会系统性低估平均摄入并掩盖未记录；仅对有记录天取均值，坚持情况另行报告。

## 后续工作

- 专门的目标预测（根据斜率推算到达目标体重的日期）。
- 在 Insights 中呈现平台期检测（引擎已能对平台期分类）。
- 更丰富的图表、体重区间带，以及按自然周而非滚动窗口统计。
- 宏量依从性（不仅能量）、饮水与体脂趋势。
- 导出 / 分享，以及可选地从 Health Connect / HealthKit 读取外部数据。

## 待解决问题

- Insights 默认窗口应为 7 天还是 30 天？（建议：7 天。）
- 达标判定是否应在预算附近使用小容差带而非 `<=`？在有依从性数据前暂缓。
