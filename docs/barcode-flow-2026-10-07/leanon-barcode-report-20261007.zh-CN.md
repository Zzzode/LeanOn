## 实际原因

1. 两端源码已有相机扫码、OFF 查询和食品导入，并非所有入口没有实现。
   旧页面直接调用相机，遇到无相机/无权限/旧宿主时只显示宽泛失败，没有可继续记录的条码输入与恢复路径。
2. Bridge 丢弃原生 `details/retriable`，查询 helper 又合并多类错误。
   Android 畸形 OFF 响应曾被当作“找不到”，这些原因不能靠改按钮文案解决。
   后续 Android 实测还暴露同值条码回填触发输入事件、误清失败提示；SDK 字节码和真实查询复核支持这一根因。
3. 本机 iOS 正式应用的实际二进制和页面包比当前工作区旧；这里只读取构建，不启动应用或读取记录。
   这证明本机存在旧安装，不能据此断言用户未知设备的失败原因。
4. iOS 模拟器源码明确无相机；Android QA 设备权限未申请。
   实际相机识别和权限首次申请仍须获得单独授权并使用合适设备；手动输入与位图解码不替代这项验收。
5. 原生复测还发现 Android 返回键关闭整个饮食表单、iOS 键盘遮挡份量输入。
   首个候选包 `ab498113…` 的 iOS 结果为 3 通过、1 失败，不能把已查到食品算作已保存饮食。

## 本轮完成的实现

- 增加只读相机/权限/宿主预检和独立手动条码入口。
  相机启动留在明确的用户动作后；手动查询不申请相机权限。
- 区分设备无相机、权限未申请/拒绝/受限、宿主缺失、能力不支持、离线、超时、服务响应、无产品、缺能量、容量计量与持久化失败。
  保留条码，提供重试、回食品搜索和手动创建；错误靠近操作区；原生同值回填保留错误与重试，只有用户改变条码才清除。
- 统一 GTIN-8/12/13/14 校验位与全零拒绝，UPC-A 规范化、UPC-E 展开，有效候选和重复帧 gate。
  旧 12 位 UPC 食品身份保留兼容，不迁移历史记录。
- 公共 OFF 请求只发送产品码。
  kcal/kJ、钠/盐统一在纯 TS 转换；明确容量产品不能当作 100 g，未知份量单位不能默认当克。
- 查询、目录导入、饮食保存分别处理。
  取消与旧响应不能触发过期导入；写入阶段阻止关闭；同一产品可重复进入确认。
  收藏/目录刷新不重置份量，编辑名称不丢失未开放编辑的微量营养字段。
- 保留原记录日期和餐次；进入产品后明确按 100 g 确认，再由用户改份量保存。
  新增/编辑的连续性修复使用实际 Lynx 原生滚动 API。

详细源码行号、契约和每项审计结论见 [源码审计](audit.zh-CN.md)。
架构记录见 [RFC 0033](../../rfcs/0033-barcode-recovery-and-product-units.zh-CN.md)。

## 仍未实现或未完成验收

| 入口/限制 | 当前状态 | 后续决定或验收 |
|---|---|---|

| 离线、超时、畸形响应、导入失败 | 分型实现及测试夹具覆盖。 | 不把夹具宣称真实断网或原生故障截图。 |
| Me 饮食偏好 | 仍为未实现入口。 | 本地偏好模型、持久化、筛选和未知食品属性的范围需定；不能承诺过敏安全。 |
| Me 数据导出 | 仍无导出/分享契约。 | 明确 CSV 或完整版本化快照、导出目的地及敏感数据处理，再实现本地文件/原生分享。 |
| Partner | 仍为本地模式，没有伴侣账号/关联/共享后端。 | 先决定身份、双向同意、授权、同步和冲突设计；没有用假 cheer 或登录占位冒充完成。 |
| 健康、提醒、体脂秤 | 现有原生能力，页面按完整方法组判断宿主支持。 | 真实提供方权限、设备和秤硬件仍需独立验收。 |
| 营养完整性 | 缺值仍落为数值 0；没有完整计量基础元数据。 | 未知不等于真实零；需模型与 UI 扩展，当前不能保证全部 OFF 产品计量基础。 |

饮食偏好建议先采用本地标签与筛选，不接账号或医疗建议；明确食品属性未知时的表现。
导出建议先提供按记录类型分开的 CSV，使用原生分享，并让用户主动选择目的地；如要求可恢复备份，再新增版本化快照格式。
Partner 的实现先出身份与双向授权 RFC，再选择同步服务，不能用本地动画代替真实关联。

旧 Android 安装若缺少早期权限申请标记，仅凭公开权限 API 不一定能完整区分历史永久拒绝；需要设备实际状态，不能伪造已授权。

正常 iOS 已安装应用仍为旧构建，本轮验证的是隔离 QA 新构建。
源码完成与“用户设备已更新”是两项不同结果；这里不宣称已替换正式安装。
真机下一步需要用户明确 iPhone 或 Android、设备及系统版本，并单独批准相机权限申请和条码拍摄；只用于公开固定条码验证，不上传照片或健康记录。
