### Exact current wire and ordering

`DELETE /v1/accounts/current` body is `{password,operationId,proof}`; proof is independent random32 bytes in canonical base64.
A domain-separated SHA-256 of `["leanon-account-deletion-v1",operationId,accountId,proof]` is stored server-side, never raw proof.
Both `POST /v1/account-deletions/:operationId/receipt` and `/ack` have body `{proof}` and do not require the deleted bearer session.
Unknown/wrong capabilities return 404 `deletion_not_found`; a generic 404, 401, timeout or missing receipt never establishes success.
Receipt query rewrites through the serialized durability barrier, so a post-rename 503 cannot be mistaken for confirmed durable deletion.
Session authorization/account/device and password snapshot are revalidated inside the DELETE transaction.

The native phases are `prepared`→`confirmed`→`local-complete`.
`prepared` can include a dispatched request with unknown outcome; it is not safe cancellation evidence.
First persist encrypted operation/account/realm/choice/revisions; only then send deletion HTTP, never persist password.
Recover by proof query first, reuse the operation, and request password reentry only if receipt is absent.
A matching durable receipt permits a durable confirmed state with revoked credentials.
For local deletion, the multi-store transaction records the local-cleared marker; cleanup failures retain it and never rewipe.
After local completion is durable, clientACK may remove the server receipt; only acknowledged/known-absent receipt in this phase permits clearing the private preparation.
Proof therefore remains until durable local completion and ACK, not merely remote confirmation.
Receipts have no automatic expiry; reaching count/state capacity refuses deletion before purge.
A lost ACK response can safely retry; this is recoverable local/file-backed behavior, not distributed atomicity or protection from lost server storage.

Accepted external-actor boundary: if another device deletes the account or revokes authorization before this operation commits, this client's prepared capability may have no matching receipt.
The client preserves preparation and does not infer deletion from404; server cancellation/tombstone reconciliation is outside this minimum protocol.
No unsafe cancel or distributed-atomic claim is added.

Backend-version boundary: root reports the existing loopback8787 service intentionally remains on the older protocol.
A new client pointed at that service can persist preparation, then receive an unknown receipt route and retain the intent; generic route404 is not deletion confirmation.
The new receipt/ACK protocol therefore requires coordinated server-first rollout or tested readiness/capability negotiation before production; rolling compatibility is not established.
The old service was not restarted or reused to work around review; the specifically approved fresh-relay retry succeeded, AndroidD now passed its originally approved consent/import/sync on the old checkpoint, with cleanup subsequently verified.
